Estágios do pipeline
Estágio 1
Coleta de dados — Treinamento
GEE → TFRecord compactado → Google Drive
▶

Exporta patches 256×256, 5 bandas (blue, green, red, pvi, pvpi) + rótulo binário, como TFRecord compactado para o Google Drive. Dois sub-pipelines: grade regular ao redor das regiões + patches extras dentro das FVs confirmadas para balanceamento. Os rótulos de 2024 podem ser pré-computados uma vez (ver alerta abaixo) em vez de recalculados a cada shard.

Entradas

  • NICFI Monthly (Planet) — 4,77 m/px
  • Rótulos FV por ano (2022–2025), asset layers_energia
  • Geometrias de região (GEE asset, 2024: shp_area_fotovoltaic_samples_update_16_05_2026)
  • Parâmetros: YEARS, REGION_INIC, REGION_END, STRIDE_PIXELS (230px)

Saídas

  • Drive/DS_FV_NICFI_TFR_V3/<year>/<region>/*.tfrecord
  • Patches 256×256×5 + label 256×256×1
  • Relatório de tasks: relatorio_tasks_tfrecord.txt

Scripts

src/preprocessing/download_dataset_tfrecord_fotovoltaica_precomp.py
Script principal — exporta TFRecords via ee.batch.Export.table.toDrive(fileFormat='TFRecord')
src/preprocessing/export_labels_2024_asset.py
Pré-exporta rótulos 2024 como assets GEE (roda uma vez para evitar recomputação)
src/preprocessing/gerenciar_tasks_tfrecord.py
Monitora fila de tasks GEE; cancela tasks travadas (RUNNING/READY)
src/preprocessing/inGEE/get_id_regions.py
Recupera IDs das regiões no GEE
ℹ️ Para 2024, rodar export_labels_2024_asset.py antes do script principal elimina um bottleneck de recomputação por task.

Estágio 3
Treinamento — Google Colab (GPU A100)
UNet + Backbones — saída: .keras salvo no Drive
▶

Treina o modelo de segmentação semântica (Focus U-Net + backbone) no Google Colab com GPU A100. A versão atual (train_fotovoltaica_colab_v2.ipynb) usa entrada (256, 256, 5) — o notebook v1 (train_fotovoltaica_colab.ipynb) usava 8 bandas e segue arquivado como referência dos modelos "L9" ainda servidos no dashboard. Saída: máscara binária (256, 256, 1).

Entradas

  • Dataset split + balanceado (TFRecords train/val/test)
  • Cabeça + backbone configuráveis (segmentation_model_factory.py)
  • Hiperparâmetros (epochs, batch, lr)

Saídas

  • best_5L_<backbone>_<timestamp>_v3.keras → Drive
  • history_<backbone>_<timestamp>.csv (nem sempre gerado — ver nota)
  • Logs TensorBoard
Arquitetura (notebook v2 atual)
Cabeça: Focus U-Net (USE_ATTENTION=True)
Backbone atual: inceptionresnet (BACKBONE_NAME)
Input: (256, 256, 5) bandas
Output: (256, 256, 1) máscara
Loss: Focal Tversky + Boundary (α=0.3, β=0.7, γ=1.25)
Métricas-alvo: Dice ≥ 0.95 · BinaryIoU (thr 0.75)
Configuração (v2 vs v1)
Epochs: 250 · steps/epoch: 250 (v1: 200)
Batch size: 46
LR: 1e-4 (v1: 1e-5) · ReduceLROnPlateau
Normalização: ÷ 10000
Filtro de patches vazios ligado: EMPTY_PATCH_KEEP_RATE=0.25 (v1 definia mas não usava)

Scripts

src/processClass/balance_tfrecord_dataset_colab.ipynb
Novo — corrige desbalanceamento em disco antes do treino: de ~1029 shards de treino, 15% dos patches eram positivos (neg:pos ≈ 5,7:1); shards 100% negativos vão para quarentena (train_sem_alerta/) e só o suficiente volta para atingir neg:pos = 3:1
src/processClass/train_fotovoltaica_colab_v2.ipynb
Notebook de treino atual — Focus U-Net + backbone configurável, 5 bandas
src/processClass/train_fotovoltaica_colab.ipynb
Notebook v1 (arquivado) — 8 bandas, gerou os modelos "L9"
src/processClass/train_fotovoltaica.py
Alternativa local (sem GPU obrigatória)
src/processClass/segmentation_model_factory.py
Factory: 5 cabeças (unet, deeplabv3plus, pspnet, fpn e a nova segformerb5) × 11 backbones (todos weights=None); ver arquiteturas_modelos_deep_learning.html
src/processClass/custom_losses.py
Registra objetos customizados para tf.keras.models.load_model()
ℹ️ segformerb5 (cabeça transformer MiT-B5) foi adicionada ao factory mas ainda não tem nenhum treino registrado em models_index.json — disponível, não validada.
⚠️ Inconsistência conhecida: o módulo custom_losses.py define boundary_weight=0.85 por padrão, mas o notebook de treino redefine a função inline com boundary_weight=0.25 (≈67% Tversky + 33% boundary) — é essa segunda versão que efetivamente roda no treino.
⚠️ Após o treino, baixar o .keras do Drive para o servidor local antes da inferência. Os 4 checkpoints "L5" mais recentes (efficientnetb7, inceptionresnet, resnet152, resnext50) não têm CSV de histórico no repositório — sem métricas finais registradas até o momento.
Estágio 4
Coleta de dados — Inferência (patches)
GEE → TFRecord / NPY sem rótulo → Drive
▶

Baixa patches sem rótulo para rodar inferência. Dois modos disponíveis:

Opção A — NPY direto (legado)
ee.data.computePixels()
Sem consumo de task quota
Saída: <region>/<year>/patch_*.npy
Limite: 1 req/s
Opção B — TFRecord GEE (recomendado)
ee.batch.Export.table.toDrive()
Múltiplos patches por task
Pré-processamento idêntico ao treino
Melhor para volume grande

Scripts

src/posprocessing/download_predict_as_tfrecord_fv.py
Script principal (Opção B) — exporta patches de inferência como TFRecord
Uso
python download_predict_as_tfrecord_fv.py \
    --year_inic 2016 --year_end 2025 \
    --region_inic 0 --region_end 90
Estágio 4b
Export mosaico TIF NICFI → Drive
GEE → GeoTIFF 5 bandas por região/ano → Drive
▶

Exporta o mosaico NICFI completo (mediana jul–dez, mesmo cálculo de pvi/pvpi da coleta de treino) de uma região como GeoTIFF multi-banda para o Drive. Usado quando a inferência roda sobre TIFs em vez de patches NPY. Há duas variantes com a mesma lógica de mosaico, diferindo apenas na seleção de regiões e no controle de progresso.

Entradas

  • NICFI (GEE) + geometria da região
  • Ano, id_region

Saídas

  • Drive/dataset_fotovoltaica_TIFreg/<id>_<ano>.tif
  • 5 bandas: blue, green, red, pvi, pvpi

Scripts

src/posprocessing/export_mosaicTIF_GEEtoDrive.py
Variante geral — lê as ~91 regiões candidatas de shp_revisao2_16_05_2026_buffer_fotovoltaic_5km; seleção via --pairs, --region-ids ou --region-start/--region-end × --years
src/posprocessing/export_mosaicTIF_GEEtoDrive_rural.py
Variante rural — lê só as células da grade nacional que intersectam fotovoltaic_rural (ver Estágio 9); progresso rastreado em src/dados/log_rurais/*.json, sem reconsulta ao GEE
ℹ️ Ordem das bandas no TIF: 1=blue, 2=green, 3=red, 4=pvi, 5=pvpi. RGB usa src.read([3, 2, 1]).

Lógica de decisão espectral (conjunto de 8 bandas)
NIR alto? → Solo / Vegetação ├─ RI alto? → Solo exposto / área queimada └─ RI baixo? → Vegetação densa NIR baixo? → Alvo escuro (IIA alto) ├─ PVI alto? → ☀️ Painel solar (Blue relativamente alto) └─ PVI baixo? → 💧 Água / sombra
ℹ️ No conjunto de 5 bandas, iia/ri/evi foram removidos e pvpi foi adicionado; não há uma árvore de decisão em cascata formalizada para esse conjunto novo no código — pvi mantém o papel principal de separar alvos escuros (painel/água/sombra) do restante, e pvpi ajuda a distinguir painel de solo/vegetação dentro desse grupo escuro.
